# 协作规范

## 开发职责

AI 开发助手负责需求拆解、技术方案、前后端实现、数据设计、测试、运行验证和文档维护。实现时优先沿用项目已有技术栈与代码风格。

## 迭代方式

每轮迭代应明确目标、验收标准、实际修改、验证结果、已知问题和后续事项。

遇到需要项目负责人判断的问题时，每轮只讨论一个明确决策点，确认后再进入下一个问题。讨论前应说明决策背景、为什么需要现在确认以及会影响哪些后续工作；像评审稿一样展开候选方案的规则效果、用户体验、实现复杂度、风险、测试和长期影响，并明确推荐项及理由。默认邀请项目负责人用自然语言自由表达、组合或修改方案，不把预设选择题作为默认交流形式；只有答案确实离散且适合快速确认时才使用选择题。能够从已确认需求、代码事实或低风险合理默认值中直接确定的事项不重复提问。

只有较大的、可识别的功能或架构变更才分配版本号，并在 `CHANGELOG.md` 中记录。小范围修复、文案调整、样式微调和内部整理不单独升级版本，仅在 `docs/history/PROJECT_LOG.md` 中记录。

版本号采用语义化格式：

- 主版本：存在不兼容变更或产品形态发生重大变化。
- 次版本：新增较大功能或形成新的可验收阶段。
- 修订版本：需要正式发布的缺陷修复。

是否构成较大变更存在争议时，由项目负责人确认。

## 关键把关点

以下事项必须由项目负责人确认后才能实施或执行：

- 产品范围、核心玩法或主要用户流程变化。
- 技术栈、系统架构或数据库模型的重大调整。
- 登录、权限、付费、隐私和数据保存策略。
- 删除数据、不可逆迁移或其他高风险操作。
- 引入付费服务或产生持续成本。
- 正式发布或部署。
- 明显影响工期或长期维护成本的方案选择。

没有项目负责人的明确指示，不执行提交、推送、正式发布或重要数据删除。

## Git 分支策略

项目保留 `master` 单分支直接开发，不建立 `feature/*`、`develop` 或 `release/*` 分支。单分支不等于自动提交：关键提交、推送、正式发布、破坏性变更和重大架构调整仍须由项目负责人确认。

每次准备提交时，应先说明本轮目标、文件变更、验证结果、已知问题和建议提交说明；获得确认后才能执行提交。

## 记录要求

项目采用双层留档：重要会话保存可导出的完整脱敏聊天稿，同时维护结构化项目记录。聊天稿用于保留讨论语境，结构化记录作为当前有效需求、决策和实施结果的权威入口；两者冲突时，以较新的已确认结构化记录为准。

- `docs/history/chat/INDEX.md` 索引重要会话的完整脱敏聊天稿。
- `docs/history/COMMAND_LOG.md` 记录项目负责人发布的核心命令、发布时间和落实情况。
- `docs/notes/DECISIONS.md` 记录关键决策、备选方案及最终结论。
- `docs/acceptance/REQUIREMENTS.md` 维护当前有效需求和验收标准。
- `docs/tasks/TASKS.md` 与 checklist 实时记录任务和检查点。
- `docs/history/PROJECT_LOG.md` 记录每轮已完成工作的具体变化与验证结果。
- `CHANGELOG.md` 只记录带版本号的较大变更。

核心命令应忠实概括原意，不把一般讨论或临时提问纳入记录。重要会话聊天稿保留用户与助手可见的完整对话，不保存系统提示、工具内部消息、密钥、敏感接口地址或其他不应入库的信息；必要时以明确占位符脱敏，不得静默改写原意。时间统一使用北京时间，格式为 `YYYY-MM-DD HH:mm:ss +08:00`。若历史消息无法取得精确时间，应明确标为“具体时间不可用”，不得推测。

## 语言规范

项目文档、界面文案以及代码注释尽可能使用中文。变量名、函数名、接口字段、标准协议名和第三方工具要求的固定文本继续使用英文。

代码只在业务意图、复杂算法、边界条件或设计取舍不够直观时添加注释，避免为显而易见的代码添加重复说明。
